# v0.13.0-ipad — A looping GIF, and the guest screen shows the strip again

**Download `photobooth-v0.13.0-win-x64.zip`, unzip, run `Photobooth.Server.exe`.**
Then open <http://localhost:5000/operator>.

> The version at the foot of the rail reads **`0.13.0-ipad`**. Please quote it
> with any result.

## New: every session also gets an animated GIF

A looping copy of the strip, saved as **`strip.gif`** beside `strip.jpg`, with
the photos **rotating through the slots**. Every slot always shows a different
photo, all of them stay visible, and the frame art sits still. The first frame is
the printed strip exactly, so the loop opens on the picture the guest already
has.

Guests get it in the gallery alongside their photos, labelled *The animation*,
and it is in the download-all zip. A real session comes out around **160 KB**, so
it downloads over the booth's own wifi without anyone waiting.

**Why a GIF and not something better.** Animated WebP is smaller and sharper and
the app could already make one with no extra parts. It is also the wrong format
here: a guest saves this to their camera roll and sends it to someone, and iOS
commonly saves an animated WebP as a still while messaging apps strip the
animation. A GIF plays everywhere, which is the entire point of making one.

**There is a switch.** *Setup → Animated GIF*. On by default; it adds about a
second per session, which is worth having back if a queue is building. It can
never cost you a session either — if building the GIF fails, the session keeps
its strip and photos and carries on.

## Fixed: the guest screen showed an empty white box

On v0.12.3 and earlier, the iPad said **"All done"** above a blank white frame
where the strip should be.

The strip is served from a route where the network port allowed only one file —
the QR — so the strip itself came back as "not found", and a broken image is all
a browser can show for that. **The operator console was never affected**, which
is what made it hard to spot: the booth's own screen looked perfect while the
guest's did not.

Fixed, and the record that carries a guest's private link is still refused on
that port, verified by test and by trying it.

## What to test

1. Run a session and watch the **guest screen**: the strip appears where the
   white box used to be.
2. Open `strip.gif` from the output folder. It should loop, with every photo
   visible in every slot over the cycle and the frame art still.
3. From a phone on the booth wifi, open the gallery: *The animation* is listed,
   plays in the page, downloads, and is in the zip.
4. **Save it to the camera roll and check it still moves there.** That is the
   step that decides whether the feature is worth anything.
5. Turn the switch off in Setup, run a session, and confirm no GIF appears and
   nothing else changes.
